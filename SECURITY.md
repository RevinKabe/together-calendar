# Security model

## Content encryption

Each space uses a cryptographically random 256-bit key generated in the browser. It is separate from account credentials and is never uploaded or put in invitation URLs. By default it stays only in tab memory. The optional **Remember the key on this device** feature stores a non-extractable CryptoKey in this browser's IndexedDB; it never stores the recovery-key string. Users must still keep the recovery key in a password manager and share it privately. Losing all copies permanently loses access to the content.

`site/crypto.js` uses the browser's native Web Crypto AES-GCM with a fresh random 96-bit nonce and a 128-bit authentication tag for every encryption. Version, workspace UUID, key epoch and record UUID (or the name marker) are authenticated as additional data. This prevents moving ciphertext between records/spaces/epochs without detection. JSON is padded to 512-byte blocks before encryption. Block counts remain visible. Imported keys are non-extractable CryptoKey objects held in memory; this is not protection against malicious same-origin JavaScript, which could use a key to decrypt.

All calendar/task content, including record kind and dates, is encrypted. Space names are encrypted too. Supabase stores ciphertext, public nonces, record/workspace/user identifiers, memberships/display names, creator IDs, timestamps and sizes. Supabase Auth handles login email addresses, password verification and MFA secrets. Account credentials are not end-to-end encrypted from the authentication provider. Passwords are sent to Supabase over HTTPS for verification; they are never stored in the app's calendar tables or repository.

## Access controls

All app tables have PostgreSQL row-level security. The anonymous role has no table privileges. Authenticated users must have `aal2` MFA assurance and belong to the space for data access. Column-level grants restrict editing to ciphertext, with constrained insert/delete access. Membership and owner actions use narrowly scoped security-definer functions with empty search paths and explicit checks. Invitation secrets are high entropy, expire after seven days and are stored only as SHA-256 hashes in a private, unexposed schema. Link fragments keep newly generated invitation tokens out of ordinary HTTP request URLs, but links are still bearer membership secrets.

An invitation grants membership after account/MFA verification; it does not carry the encryption key. Any verified holder of the invitation may join until it expires or is revoked, so send it only to intended recipients. Anyone with both membership and the content key can read and modify the space. Members cannot change ownership or rotate keys. The public publishable API key is deliberately public and conveys no administrative privilege.

The current deployment uses one shared app account for two people and has public signups disabled. Both people have the same identity, MFA factor and owner permissions; activity cannot be attributed to either person and access cannot be revoked individually. App account sharing does not require sharing GitHub or Supabase administrator access. The frontend signup flag is only a display control; the matching Supabase setting enforces closed registration.

Owners rotate all current ciphertext atomically using a fresh key and epoch. Rotation checks the complete record set and prior timestamps, rejecting concurrent edits rather than losing them. Removing a member performs the same rotation and revokes pending links. Remaining members need the new key. Authorized members can retain any plaintext, old key or ciphertext they already downloaded; removal cannot erase their copies. This is shared-key encryption, without per-device identity verification, forward secrecy or cryptographic attribution of individual writers.

## Browser and deployment boundaries

Accounts can enroll multiple independent TOTP authenticators. The app lists only verified TOTP factors and submits the selected factor's ID for login and remembered-key unlocking. Adding another phone requires fresh verification of an existing factor in the app, an `aal2` session, and successful verification of the newly enrolled factor. This extra freshness check is an application flow, not a separate server policy beyond Supabase's MFA enforcement. QR codes and manual setup secrets are displayed only during enrollment, never persisted by the app, and cleared on close, lock or sign-out. Phone labels and TOTP secrets are handled by Supabase as authentication metadata; they are separate from the calendar encryption key. Enrollment does not modify content encryption, saved keys or existing verified factors. Cancellation serializes cleanup after pending requests and removes only the new factor if still unverified; interrupted/offline cleanup can leave unused unverified factors. No verified-factor removal UI is exposed.

Login tokens stay in memory with `persistSession: false`. Refreshing the page requires a new login and MFA; only after MFA does the app read saved keys for spaces returned by the server's membership policies. Stored key identities include the backend/app scope, account UUID, workspace UUID and key epoch. Stale versions, revoked memberships and malformed/extractable keys are rejected or removed. Saving is opt-in and only attempted after successful content decryption or explicit creation/rotation. Storage failures are reported rather than silently claiming persistence.

Lock clears in-memory key references, decrypted collections, forms and rendered content; idle locking runs every 15 seconds after a five-minute inactivity threshold, and rechecks on visibility change. Lock does not delete an opted-in saved copy. The app requires a fresh successful authenticator challenge before reusing a saved key after Lock, while the existing authenticated session remains until sign-out or expiry. This additional UI challenge is not a new server-side session downgrade and does not cryptographically protect the local key. Normal polling never automatically unlocks a manually locked space.

**Device key → Forget this key and lock** removes the current saved key and locks local content. The sign-in page can remove all saved keys for this app, including other accounts, without affecting other app scopes. Removal notifies other open tabs to lock; saving a key in another tab does not auto-unlock them. Signing out deliberately retains opted-in keys. Changing the space key invalidates older copies; retaining the preference updates the current browser's saved copy after successful rotation. Independent browsers require the replacement recovery key.

Non-extractability prevents Web Crypto's export/wrap operations, not use of the key to decrypt. IndexedDB is not guaranteed to be hardware-backed or encrypted with a user-held secret. A person or malicious program with access to this browser profile, or same-origin JavaScript, may use saved keys outside the app's MFA flow. This feature preserves encryption from the database provider but increases endpoint exposure compared with memory-only keys. The TOTP code is never used as an encryption key. JavaScript cannot promise physical memory erasure or deletion of clipboard history, browser/OS caches, screenshots, crash dumps or device backups. Clear the clipboard after saving a recovery key and use this feature only on trusted devices.

HTML text is escaped, scripts/libraries are local, and the CSP limits scripts/styles to this origin and network access to the configured Supabase endpoint. Referrers are suppressed and crawler directives request no indexing. Those directives are voluntary: they are not authorization controls. Public source and the login/demo page are visible to anyone. GitHub Pages does not provide per-repository custom security headers; the app has a frame guard, but cannot claim header-level frame protection or origin isolation from other pages hosted on the same `github.io` origin.

The browser receives executable code from GitHub Pages on every load. A compromised GitHub account, malicious deployment, dependency update, extension, browser, device or authorized recipient can expose plaintext/keys while the app is unlocked. Database encryption does not prevent those attacks. Protect GitHub and Supabase administrator accounts with MFA, review deployments/dependencies, and use trusted devices. Backend operators with only stored ciphertext cannot decrypt it without the key, but authentication and operational metadata remain accessible to the providers. No claim of absolute human/AI/crawler exclusion or independent security certification is made.

## Availability and recovery

Supabase Free limits, pauses or account/service loss can make the app unavailable. End-to-end encryption does not prevent record deletion, server rollback, traffic analysis or denial of service. Maintain encrypted database backups separately from recovery keys. A password reset restores account access only; it cannot recover the content key or a lost authenticator setup. Retain secure authenticator backups and arrange account recovery with the project owner if necessary.

## Validation and reporting

Automated Web Crypto/unit tests and PostgreSQL policy tests exercise the real application modules/schema. Browser checks use fictional data and a local mock backend. The native browser storage suite exercises persistence, key non-extractability, scope isolation, changed epochs, deletion ordering and unavailable storage. App browser checks cover opt-in, reload/MFA gating, remembered-key unlocking after Lock, rotation and forgetting. Live read-only checks verify anonymous table denial, private-schema exclusion, email confirmation, anonymous-login settings and the closed-signup policy. The account owner completed private account setup. Real multi-device synchronization and an independent security audit remain unverified; automated checks do not provide a security certification.

Do not post passwords, recovery keys, invitation links or private calendar data in public GitHub issues. Report a suspected vulnerability privately to the repository owner, using a channel you already trust.
